# ADR-0012: Client data layer — TanStack Query for reads, generated API types

- **Status:** Accepted (2026-07). The rule that every write goes through the outbox is narrowed: setup and administration writes are direct and online-only ([ADR-0022](0022-event-and-division-management.md) §7).

## Context

The app had no read cache: every navigation refetched from empty, screens blanked on refetch, and manual "Refresh" buttons stood in for invalidation. API responses were unchecked casts against hand-mirrored types, so a renamed server field became a runtime `undefined` instead of a build error. The write path, the offline outbox ([ADR-0002](0002-offline-sync-design.md)), was the strongest part of the app and must not be weakened by any change here.

## Decision

### Reads: TanStack Query

- **TanStack Query owns every server read**, over the existing typed fetch wrapper. Cached data renders at once and revalidates in the background; a screen never blanks.
- **Query keys follow the resource path**, so two screens reading the same resource share one cache entry and one request.
- **The outbox drain drives freshness.** Writes do not update the read cache; after a pass in which the server accepted anything, every cached query is marked stale and refetches when next shown. Queued captures render from the outbox's own live queries, not from the read cache: a queued result is visible because it is queued.

### Types: generated from OpenAPI

- The API emits an OpenAPI document; the client's types are generated from it into `app/src/api/generated.d.ts`, committed, and regenerated by a script, so a build needs no running API. CI checks the file is current, so a contract change shows up as a diff and a type error.
- The client's error type is a widening of the generated `{ error, detail }` shape ([ADR-0011](0011-api-error-contract.md)), because a few codes carry extra fields the schema does not describe.
- Outbox payloads are a discriminated union keyed on `kind`; they are capture-time shapes the app owns, checked against the generated request bodies.

### Writes

- **No write uses `useMutation`.** Captures on the deck (results, attempts, jumps, entries, relay teams, placements, races minted on the deck, adjustments) go through the outbox.
- **Corrections** are sent directly while online, so a revision clash reaches the official at once, and fall back to the outbox if the request fails in transport.
- **Setup and administration** (carnival setup, schedule, event status, finalisation, settings, imports, roles, voids) and two deck controls (raising the high-jump bar, attempts per height) call the API directly and refuse plainly when offline.

How it works: [offline outbox § what goes through it](../architecture/offline-outbox.md#what-goes-through-it).

## Consequences

- Navigation stops refetching from empty; caching, deduplication and reconnect revalidation come from one mature dependency.
- Two build-time concerns: an OpenAPI document from the API and a committed generated file.
- The read/write split must be defended in review: reaching for `useMutation` on a capture path is an invisible mistake until a device goes offline.
- Query metadata gives screens a free "last updated" signal for cached reads.

## Rejected alternatives

- **A hand-rolled URL-keyed cache**: small to start, but grows into deduplication, retry, focus and reconnect revalidation and invalidation, all owned and tested in-house.
