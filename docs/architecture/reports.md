# Reports and exports

Reports are computed on read from the results every device has synced; nothing is stored or cached. There are three outputs: the **reports screen** (standings, results book, records), which prints to paper or PDF through the browser; three **CSV exports** generated by the server; and the **printable program**. There is no public or venue display.

## Who sees what

| Output | Route (app) | API | Roles |
|---|---|---|---|
| Reports screen and results book | `/carnivals/{id}/reports` | `GET /api/v1/carnivals/{id}/reports/results` | CarnivalAdministrator, SystemAdministrator |
| Standings CSV | Download button on the reports screen | `GET …/reports/standings.csv` | CarnivalAdministrator, SystemAdministrator |
| Results CSV | Download button | `GET …/reports/results.csv` | CarnivalAdministrator, SystemAdministrator |
| District selection CSV | Download button | `GET …/reports/district.csv` | CarnivalAdministrator, SystemAdministrator; Finalised carnivals only |
| Printable program | `/carnivals/{id}/program` | carnival, schedule and event reads | every signed-in role |

The whole `/reports` group is behind `carnivals:administer`: a file of student names leaving the platform is a staff-desk act, not part of the read surface every role holds. The live standings read the dashboard uses (`GET …/standings`) stays on `carnivals:view`. See [ADR-0004](../adr/0004-reporting-and-publishing.md).

Reports work in any carnival status. A Draft carnival's book is empty rather than refused; a Finalised carnival's reports stay readable indefinitely.

## Reports are online only

Reports are read directly from the API, never through the outbox, and the service worker never caches a report read (`…/reports/*` is not on its cache allowlist). A device holds only its own captures, so there is nothing honest to build a report from offline. Without a connection the reports screen disables the export buttons and says why; a report already on screen is marked as possibly out of date.

## The reports screen

Three sections, then the browser's print dialog for paper or PDF. There is no PDF library: a `@media print` stylesheet hides the controls (`no-print`), keeps each heat's table on one page and keeps a heading with its table.

1. **House standings**, with a *provisional* badge until the carnival is finalised. The same computation as the dashboard.
2. **Results book**: one block per event and division, with a table per heat.
3. **School records** for the carnival's sport, and, once the carnival is finalised, the records set at this carnival.

### The results book

One row per recorded result (any lifecycle state except Draft), from `ResultsBook.BuildAsync`:

- **Order:** event code, then age (youngest first), category, tier; within an event, by heat (unheated last), then place, then name.
- **Places** come from the same placing code that pays house points, inside the same pools: a timed event is placed per heat (two heats print two firsts, as they score two firsts), and a field event is one field however many flights it ran. Results that are not `Ok` (`DNS`, `DNF`, `DQ`, `NM`) have no place, and neither does any row of an event scored as Social.
- **Values** are formatted in the measure's unit (times, metres to two decimals). A high-jump result carries its attempt card, fails at best height and total fails; the screen prints the card with the countback rule. A high-jump card whose only marks were cleared away is not a result and is left out.
- **Names and houses** are the entry's snapshot, taken when the student was entered.
- `Provisional` is true until the carnival is Finalised.

A row shows the division label (for example `13 Boys`, `All ages Open`) but never a student's own category ([ADR-0026](../adr/0026-the-student-category-is-server-side-only.md)). The screen adds a record badge to a Competitive result that strictly beats the standing school record (equalling is not enough).

## CSV exports

| File | Columns | Rows |
|---|---|---|
| `standings-<carnival>-<date>.csv` | Rank, House, Placement points, Participation points, Bonus points, Total | One per house the standings list (every configured house, or once finalised the houses that took part; plus any house with scoring rows), in leaderboard order. Rank is the shared rank the screen shows: houses level on points share it and the next rank skips (1, 1, 3, 4). |
| `results-<carnival>-<date>.csv` | Event code, Event, Division, Tier, Heat, Place, Name, House, Result, Status, Series, Fails at best, Total fails | The results book, row for row. Series is the high-jump card, for example `1.25 O · 1.30 XXO`. |
| `district-<carnival>-<date>.csv` | Event code, Event, Division, Selection, Name, Year level, Result | District team selection (below). |

`<carnival>` is a lower-case slug of the carnival name and `<date>` is the carnival date as `yyyy-MM-dd`.

### District team selection

The one export designed to leave the school. It is produced only from a **Finalised** carnival (`409 CARNIVAL_NOT_FINALISED` otherwise; the button is disabled with the same explanation), because a selection process cannot see a later correction.

- For each **Competitive** division, the top two places on the event ladder: one ranking across every heat, of non-Draft `Ok` results with a measured value. The same ladder decides school records, so the district list and the record book cannot disagree.
- Individual entries only; relay teams and Social divisions are left out.
- Ties share a rank, so a tie for second gives three rows. The school breaks the tie, not the platform.
- `Year level` is the entry's snapshot. No date of birth, student ID, category or house is included. See [ADR-0028](../adr/0028-records-and-district-selection.md).

### How a CSV is written

- `text/csv; charset=utf-8` with a UTF-8 byte-order mark (Excel otherwise decodes the file in the machine's ANSI codepage and mangles non-ASCII names), CRLF line ends, RFC 4180 quoting.
- **Formula injection is neutralised.** A field starting with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe so a spreadsheet treats it as text, unless the whole field is a number (a bonus adjustment can legitimately be negative).
- Every CSV response writes a `report.export` audit event naming the report, format and row count against the carnival. Viewing the reports screen is not audited.
- Exports share the per-user `bulk-data` rate limit with roster uploads (`RateLimiting:BulkDataPerMinute`, default 10 per minute).
- Files are built in memory; a carnival produces hundreds of rows. The app saves the response through an object URL.

## The printable program

`/carnivals/{id}/program` renders the schedule built on the program builder screen as a print-ready page: the carnival name, date and venue, then one column per stream, with each slot's time (or time range), label and the events in it, one line per event listing its divisions. It carries no student names.

- A Draft carnival's program prints a DRAFT notice, because paper carries no status.
- With more than four streams the page switches to landscape; from four streams the screen suggests printing in landscape.
- Novelty-points notes on a slot are shown on screen and left off the printout.

## Venue and public display

None exists. The dashboard is the live scoreboard, for signed-in users only (any role, including Viewer). A read-only venue page and integrations with external reporting tools are directions in [ADR-0004](../adr/0004-reporting-and-publishing.md), not built.
